# Nomos Roadmap V1.3+

> 状态：Draft
> 日期：2026-06-07
> 范围：v1.3-v1.6 是 v1.2 流程管理到 v2.0 Workflow 引擎之间的产品和数据坡道。

## 1. 路线判断

v1.2 已经完成“流程模板、流程实例、阶段、关口评审”的基础能力。v1.3-v1.6 不能直接跳到完整 Workflow 引擎，而要先把真实执行中的任务、派发、资源、成本、知识和模板治理沉淀下来。

路线如下：

```text
v1.2 流程管理
  -> v1.3 工作项与进度资源看板
  -> v1.4 智能体任务调度与协作执行
  -> v1.5 资源、产能、成本与组合看板
  -> v1.6 知识沉淀、决策复盘与模板治理
  -> v2.0 Workflow 引擎
```

阶段目标：

| 版本 | 主要问题 | 关键产物 | 给 v2.0 沉淀什么 |
|------|----------|----------|------------------|
| v1.3 | 阶段下面没有可执行颗粒 | 工作项、事件账本、进度看板 | L3/L4/L5 候选任务和事实流 |
| v1.4 | Agent 派发缺少工作项上下文和审计 | 派发策略、任务信封 v2、结构化回执 v2 | 硅节点和碳硅节点的派发经验 |
| v1.5 | 资源、产能、成本不可解释 | 产能计划、资源分配、成本记录、组合快照 | 节点执行成本、资源瓶颈和组合风险 |
| v1.6 | 执行经验没有变成可复用资产 | 决策记录、知识资产、模板版本、准备度报告 | 可治理的流程模板和升级依据 |
| v2.0 | 流程不能自动调度和回放 | L2-L5 引擎、事件 reducer、节点运行日志 | 可运行 Workflow |

## 2. 不提前进入 v2.0 的能力

v1.3-v1.6 不做：

- 不做 L2-L5 完整引擎。
- 不做动态编排和自动条件分支。
- 不做硅节点自动抢任务。
- 不做跨流程编排。
- 不做运行中实例自动升级。
- 不做企业级 RBAC、云端协同和财务级账务。

这些能力统一放到 v2.0 或后续版本，避免在 v1.x 阶段把底座做散。

## 3. v1.3：工作项与进度资源看板

### 定位

把 v1.2 的流程阶段拆成可执行、可分配、可验收、可追踪的工作项。v1.3 是 v2.0 L3/L4/L5 的数据地基，但不实现自动调度。

### 范围

- 新增 `workItems[]` 和 `workItemEvents[]`。
- 工作项 CRUD、状态流转、负责人、角色、Skill、优先级、截止时间、验收标准。
- 工作项依赖：同项目内依赖、循环检测、跨项目拦截。
- 阶段映射：工作项可挂到 `flowInstances[].stages[]`。
- 旧项目兼容：旧 `workflowTasks[]` 可镜像成工作项进入看板。
- 进度看板：项目、流程模板、流程实例、阶段、负责人维度聚合。
- 资源看板初版：执行者分布、阻塞、逾期、未分配。

### 数据版本

v8 -> v9：

- `workItems: []`
- `workItemEvents: []`

### 发布门槛

- 旧 v8 数据迁移后项目、流程、备份恢复不受影响。
- 工作项写操作必须写入事件。
- 依赖未满足时不得进入 `in_progress`。
- 看板空项目返回 0/空数组，不返回 null 或报错。
- 旧五阶段项目仍可按原链路运行。

详细设计见：`产品规划/02-PRD/PRD_V1_3_WORK_ITEMS_AND_DASHBOARDS.md`。

## 4. v1.4：智能体任务调度与协作执行

### 定位

把 Agent 派发从“阶段旁边的工具调用”升级为“围绕工作项的受控执行”。v1.4 强调确认、幂等、回执、复核和可追溯，不做 Agent 自主调度。

### 范围

- 从工作项生成派发预览。
- 任务信封 v2：项目、流程、阶段、工作项、输入、验收标准、Skill、幂等键。
- 派发确认、取消、重试。
- Agent 推荐：岗位、Skill、阶段、Adapter、健康状态。
- 结构化回执 v2：完成、失败、阻塞、产物、置信度、复核建议。
- 多 Agent 协作记录：主执行、复核、交接、仲裁。
- 派发事实写入 `workItemEvents[]`，派发详情写入 `agentDispatches[]`。

### 数据版本

v9 -> v10：

- `dispatchPolicies: []`
- `agentDispatches: []`
- `agentHealth: []`

### 发布门槛

- 未确认派发不得执行。
- 重复派发不得创建多个进行中任务。
- 失败重试必须新建 attempt。
- 取消后的迟到回执不得覆盖当前状态。
- token、工作目录和敏感配置不得泄露。

详细设计见：`产品规划/04-详细规划/V1_4_AGENT_DISPATCH_AND_COLLABORATION.md`。

## 5. v1.5：资源、产能、成本与组合看板

### 定位

把 v1.3 工作项和 v1.4 派发日志聚合成经营视角：资源是否超载、成本是否可解释、项目组合是否健康。

### 范围

- 资源画像：员工、角色、Agent、混编员工。
- 产能计划：周/月容量、保留容量、超载小时。
- 资源分配：工作项估算、实际耗时、手工分配。
- 成本记录：人工、Agent、外部服务、工具、其他。
- 项目组合看板：健康状态、阶段风险、资源瓶颈、成本偏差、ROI 草算。
- 快照：保存某一时点的指标、口径和过滤器。

### 数据版本

v10 -> v11：

- `capacityPlans: []`
- `resourceAllocations: []`
- `costEntries: []`
- `dashboardSnapshots: []`
- `portfolioViews: []`

### 发布门槛

- unknown 成本和容量必须显式展示，不得当作 0。
- 聚合结果不得跨项目、跨执行者错算。
- 快照保存后不被后续实时数据改写。
- 成本敏感字段不得进入 Agent 信封。
- 旧项目无产能/成本数据时显示空态。

详细设计见：`产品规划/04-详细规划/V1_5_RESOURCE_CAPACITY_AND_COST_DASHBOARD.md`。

## 6. v1.6：知识沉淀、决策复盘与模板治理

### 定位

v1.6 是 v1.x 的收口版本。它把工作项、派发、成本、关口和复盘结论沉淀成可复用知识和可治理模板，为 v2.0 引擎升级建立准入标准。

### 范围

- 决策记录：关键取舍、备选方案、证据、影响。
- 复盘记录：项目、阶段、工作项、Agent、模板、组合维度。
- 知识资产：SOP、样例、提示词、验收准则、失败案例、最佳实践。
- 模板版本：baseline、draft、active、deprecated。
- 模板治理：变更摘要、变更原因、适用范围。
- v2.0 准备度：阶段、关口、工作项、Skill、派发策略、复盘样本、成本样本。
- 导入导出和脱敏。

### 数据版本

v11 -> v12：

- `decisionRecords: []`
- `knowledgeAssets: []`
- `retrospectives: []`
- `templateVersions: []`
- `governanceChecks: []`

### 发布门槛

- 激活模板版本不得静默改变运行中实例。
- sensitive 知识资产默认不导出。
- major 模板变更必须有摘要和确认。
- v2.0 准备度不得把缺失关键数据误判为通过。
- 导入不得覆盖本地 active 知识资产。

详细设计见：`产品规划/04-详细规划/V1_6_KNOWLEDGE_DECISION_AND_TEMPLATE_GOVERNANCE.md`。

## 7. v2.0：Workflow 引擎

### 定位

v2.0 把 v1.2-v1.6 沉淀的数据升级为可运行 Workflow：

- L2 阶段。
- L3 任务。
- L4 步骤。
- L5 节点。
- 碳、硅、碳硅节点。
- 事件驱动、ready 判断、节点调度、结构化回执、可回放日志。

### 最低进入条件

- 至少 1 条核心流程模板处于 active。
- 该模板包含 4 个以上阶段和 2 个以上关口。
- 至少有 8 个以上历史工作项样本。
- 关键阶段绑定岗位和 Skill。
- 至少 1 种 Agent 能通过 v1.4 派发链路稳定完成工作项。
- 至少有 1 份 v1.5 资源/成本快照。
- 至少有 3 个复盘或决策记录支撑模板治理。
- v1.6 准备度报告无 P0 阻断。

详细设计见：`产品规划/04-详细规划/V2_WORKFLOW_ENGINE_ACCEPTANCE_AND_ARCHITECTURE.md`。

## 8. v2.0 交接契约

| v1.x 数据 | v2.0 映射 | 说明 |
|-----------|-----------|------|
| `flowTemplates[].stages[]` | L2 阶段 | v1.2 已有，v1.6 前需要模板版本治理 |
| `flowInstances[]` | Workflow runtime session | 保留旧 `flowInstanceId` 映射 |
| `workItems[]` | L3/L4/L5 候选结构 | v1.3 工作项不自动等同节点，需迁移规则 |
| `workItemEvents[]` | Workflow 事件流 | v2.0 reducer 的事实来源 |
| `agentDispatches[]` | `nodeRuns[]` 历史参考 | v1.4 派发不是节点运行时，但可迁移执行证据 |
| `dispatchPolicies[]` | 节点路由策略 | 可升级为硅节点/碳硅节点策略 |
| `capacityPlans[]` | 节点资源约束参考 | v2.0 可先只读 |
| `resourceAllocations[]` | 节点执行资源历史 | 解释资源瓶颈和成本 |
| `costEntries[]` | 节点成本候选 | v2.0 不做财务账，但保留成本解释 |
| `dashboardSnapshots[]` | 迁移前经营快照 | 防止指标口径漂移 |
| `decisionRecords[]` | 引擎规则和模板变更证据 | 解释为什么升级某条流程 |
| `knowledgeAssets[]` | 节点输入、SOP、验收准则 | 可作为未来 Agent 上下文 |
| `templateVersions[]` | 模板版本基线 | v2.0 实例化必须基于明确版本 |
| `retrospectives[]` | 流程优化证据 | 选择适合升级的模板 |
| `governanceChecks[]` | 升级阻断项 | v2.0 启动前清零 P0 |

## 9. 发布节奏

| 阶段 | 建议动作 |
|------|----------|
| v1.2 收尾 | 修复关口绕过、旧备份 inspect/restore、流程页首次加载、无效 templateId 原子性 |
| v1.3 启动 | 先做数据迁移和 API，再做项目详情工作项和看板 |
| v1.4 启动 | 先做派发预览/确认/幂等，再做健康状态和协作 |
| v1.5 启动 | 先定指标口径和聚合 API，再做 UI |
| v1.6 启动 | 先做模板版本和知识/决策模型，再做准备度报告 |
| v2.0 启动 | 使用 v1.6 准备度报告作为工程评审输入 |
