# Nomos V1.3 到 V2.0 总体设计与交付计划

> 状态：Draft for planning and implementation
> 日期：2026-06-07
> 范围：v1.3、v1.4、v1.5、v1.6、v2.0
> 目的：把 v1.2 流程管理之后的产品坡道、工程边界、数据迁移、验收口径和 Alice 任务拆解统一到一份可执行计划里。

## 1. 总体判断

Nomos v1.2 已经把“项目可以绑定流程模板并按阶段/关口推进”这条主线搭起来。下一阶段不能马上跳到完整 Workflow 引擎，否则会出现三个问题：

1. 阶段下面缺少可执行颗粒，Agent 没有稳定的最小任务对象。
2. 执行事实没有统一账本，进度、资源、复盘和调度都会各算各的。
3. v2.0 引擎需要 L3/L4/L5、节点事件、调度日志和模板治理，如果前置数据不稳，迁移风险会很高。

因此 v1.3 到 v1.6 的主线是：

```text
v1.2 流程管理
  -> v1.3 工作项与进度资源看板
  -> v1.4 智能体任务调度与协作执行
  -> v1.5 资源、产能、成本与组合看板
  -> v1.6 知识沉淀、决策复盘与模板治理
  -> v2.0 Workflow 引擎
```

这条路线的核心不是“多做几个页面”，而是逐步沉淀 v2.0 需要的运行数据：

| 版本 | 要回答的问题 | 沉淀给 v2.0 的基础 |
|------|--------------|---------------------|
| v1.3 | 阶段里到底有哪些工作，谁负责，做到哪里？ | `workItems[]`、`workItemEvents[]`、阶段内任务树、状态流转、依赖关系 |
| v1.4 | 哪个 Agent 被派发到哪个工作项，依据什么，结果如何？ | `agentDispatches[]`、派发策略、任务信封 v2、结构化回执 v2、幂等执行日志 |
| v1.5 | 人、Agent、项目组合的产能和成本是否可解释？ | `capacityPlans[]`、`resourceAllocations[]`、`costEntries[]`、组合快照 |
| v1.6 | 哪些知识、决策和模板规则应该固化为流程资产？ | `decisionRecords[]`、`knowledgeAssets[]`、`templateVersions[]`、复盘和治理记录 |
| v2.0 | 流程能否以事件驱动方式自动调度碳/硅/碳硅节点？ | L2-L5 运行时、节点调度、事件 reducer、可回放日志 |

## 2. 版本边界

### v1.3：工作项与进度资源看板

v1.3 的最小交付对象是工作项。它把 v1.2 的 `flowInstances[].stages[]` 和旧项目的 `workflowTasks[]` 映射到统一的 `workItems[]`。

必须做：

- 工作项 CRUD、状态流转、负责人、优先级、截止时间、依赖、验收标准。
- 工作项事件账本 `workItemEvents[]`，所有状态、负责人、依赖、回执变化都必须留痕。
- 绑定流程项目的阶段内工作项展示。
- 未绑定流程的旧项目通过镜像工作项进入看板。
- 项目进度看板、阶段进度、阻塞项、逾期项、负责人分布。
- 关口评审可以读取必做工作项完成情况，但不把 v1.2 关口重写成规则引擎。

不做：

- 自动调度 Agent。
- 自动排期、容量预测、成本核算。
- 动态分支、并行执行引擎。

### v1.4：智能体任务调度与协作执行

v1.4 的最小交付对象是“从工作项到 Agent 的受控派发”。它不让 Agent 自主抢任务，而是由用户或策略发起、确认、执行、回执、复核。

必须做：

- 从工作项发起派发预览，生成任务信封 v2。
- 派发确认、取消、重试、幂等保护。
- Agent 能力路由：岗位、Skill、阶段、Adapter、健康状态共同参与推荐。
- 结构化回执 v2：完成、失败、阻塞、产物引用、复核建议、下一步。
- 多 Agent 协作记录：主执行、复核、交接、仲裁。
- 所有派发事实写入 `workItemEvents[]`，完整记录在 `agentDispatches[]`。

不做：

- Agent 自主启动执行。
- 完整多 Agent 编排引擎。
- v2.0 的硅节点自动调度。

### v1.5：资源、产能、成本与组合看板

v1.5 的最小交付对象是经营视角的可解释看板。它把 v1.3 工作项和 v1.4 派发日志聚合成资源、产能、成本、项目组合风险。

必须做：

- 资源画像：员工、角色、Agent、混编员工的工作负载、阻塞、逾期、完成质量。
- 产能计划：周/月容量、保留容量、冲突检测、超载提示。
- 成本记录：人工估算成本、Agent 调用成本、外部执行成本、项目成本汇总。
- 项目组合看板：项目健康、阶段风险、资源瓶颈、成本偏差、ROI 草算。
- 快照机制：`dashboardSnapshots[]` 或同等结构保存某一时点的指标口径。

不做：

- 自动排班优化。
- 财务级账务系统。
- 云端 BI 和多人权限。

### v1.6：知识沉淀、决策复盘与模板治理

v1.6 的最小交付对象是“可复用的组织知识与流程模板资产”。它把执行结果、成本结果、复盘结论和关键决策沉淀为可治理的模板版本与知识资产。

必须做：

- 决策记录：记录关键方案选择、评审结论、取舍理由、证据和后续影响。
- 知识资产：SOP、样例、提示词、验收准则、失败案例、最佳实践。
- 项目/阶段/Agent 复盘：从工作项、派发、成本、关口中抽取可行动结论。
- 模板版本治理：模板 draft/active/deprecated、版本号、变更摘要、基线、升级建议。
- v2.0 准备度：检查流程模板是否具备阶段、工作项、岗位、Skill、派发策略、复盘证据。

不做：

- 企业级 RBAC。
- 云端知识库。
- 自动修改模板或自动升级运行中实例。

### v2.0：Workflow 引擎

v2.0 才进入真正的 Workflow 引擎：

- L2 阶段、L3 任务、L4 步骤、L5 节点。
- 碳、硅、碳硅节点。
- 事件驱动、ready 判断、节点调度、回执 reducer。
- 并行任务、简单条件分支、返工、关口规则。
- 可回放日志和运行时监控。

v2.0 的前提不是“把 v1.2 流程模板展示得更复杂”，而是确认 v1.3-v1.6 的数据已经足够解释真实执行。

## 3. 数据迁移总线

| 版本 | 数据版本建议 | 新增顶层结构 | 兼容要求 |
|------|--------------|--------------|----------|
| v1.2 | v8 | `flowTemplates[]`、`flowInstances[]` | 旧 v7 备份可 inspect/restore，并迁移到 v8 |
| v1.3 | v9 | `workItems[]`、`workItemEvents[]` | 旧项目不强制生成工作项，按需镜像旧 `workflowTasks[]` |
| v1.4 | v10 | `dispatchPolicies[]`、`agentDispatches[]`、`agentHealth[]` | 旧 Agent 执行记录仍可打开，不强制绑定工作项 |
| v1.5 | v11 | `capacityPlans[]`、`resourceAllocations[]`、`costEntries[]`、`dashboardSnapshots[]` | 没有成本或容量数据时返回 unknown/空态，不伪造 0 |
| v1.6 | v12 | `decisionRecords[]`、`knowledgeAssets[]`、`templateVersions[]`、`retrospectives[]`、`governanceChecks[]` | 旧流程模板生成 baseline 版本，不改运行中实例 |
| v2.0 | v20 | `nodeRuns[]`、扩展 `workItems` 到 L3/L4/L5 | 保留旧 `flowInstanceId` 到新运行时的映射 |

迁移原则：

1. 迁移必须先创建保护快照。
2. 迁移必须追加字段，不删除用户原始数据。
3. 旧版本缺字段时补空数组或 unknown，不用错误默认值掩盖事实。
4. inspect/restore 必须先做迁移友好读取，再做严格校验。
5. 所有新增结构必须进入系统诊断和备份恢复回归测试。

## 5. Alice 执行拆解

后续实现建议使用多个 Alice Agent 并行，但每个 Agent 必须有明确写入边界。

### v1.3 实现组

| Agent | 负责范围 | 文件边界 |
|-------|----------|----------|
| Alice-Data | 数据模型、迁移、校验、备份恢复 | `backend/store.js`、`backend/work-items.js`、测试夹具 |
| Alice-API | 工作项 API、依赖校验、事件写入 | `backend/routes/work-items.js` 或同等路由 |
| Alice-UI | 工作项中心、项目详情工作项 Tab、看板 | `renderer/app.js` 或拆分后的前端模块 |
| Alice-QA | 自动化测试和手工验收脚本 | `tests/server.test.js`、集成测试脚本、测试报告 |

### v1.4 实现组

| Agent | 负责范围 |
|-------|----------|
| Alice-Dispatch | 派发预览、确认、取消、重试、幂等 |
| Alice-Router | Agent 能力路由、策略、健康状态 |
| Alice-Receipt | 结构化回执 v2、工作项状态联动 |
| Alice-Security | Adapter 脱敏、工作目录边界、确认 token |

### v1.5 实现组

| Agent | 负责范围 |
|-------|----------|
| Alice-Metrics | 指标口径和聚合 API |
| Alice-Capacity | 产能计划、资源冲突、超载提示 |
| Alice-Cost | 成本记录、项目成本、ROI 草算 |
| Alice-Dashboard | 组合看板、资源看板、快照视图 |

### v1.6 实现组

| Agent | 负责范围 |
|-------|----------|
| Alice-Knowledge | 知识资产、搜索、关联、脱敏 |
| Alice-Decision | 决策记录、复盘、行动项 |
| Alice-Template | 模板版本、变更记录、治理状态 |
| Alice-Readiness | v2.0 准备度检查和治理报告 |

## 6. 跨版本验收门禁

每个版本发布必须满足：

- 数据迁移自动化测试通过。
- 旧项目主链路回归通过。
- 备份 inspect/restore 回归通过。
- 新增 API P0/P1 测试通过。
- 至少一条完整手工用户路径通过。
- 发布说明、回退方案和已知风险写入文档。

v2.0 启动前必须满足：

- 至少 1 条核心流程模板为 active，具备阶段、关口、默认工作项、岗位和 Skill。
- 至少 3 个项目完成 v1.3-v1.6 的执行数据沉淀。
- 至少 1 个 Agent 能稳定通过 v1.4 派发链路完成工作项。
- v1.5 能解释项目组合资源和成本风险。
- v1.6 能输出模板治理记录、关键决策记录和 v2.0 准备度报告。

## 7. 当前已知风险

| 风险 | 等级 | 处理策略 |
|------|------|----------|
| v1.2 工作树中有未收口代码改动和测试失败迹象 | P0 for release | 作为 v1.2 收尾门禁，不混入本设计文档提交 |
| v1.3 工作项容易和旧 `workflowTasks` 双写冲突 | P0 | 采用镜像工作项和事件同步，旧链路失败不得被新链路影响 |
| v1.4 派发若无幂等会重复执行 Agent | P0 | 派发预览、确认、执行、回执必须使用 idempotencyKey 和 attempt |
| v1.5 成本指标可能被误读为财务账本 | P1 | 明确为经营估算，不做财务级结算 |
| v1.6 模板治理可能误改运行中项目 | P0 | 模板版本只影响新实例，运行中实例需要显式升级动作 |
| v2.0 一次性引擎重写风险过大 | P0 | 先以 v1.3-v1.6 数据夹具验收，再做引擎迁移 |

## 8. 下一步

1. 先冻结 v1.2 收尾缺陷，确保流程关口、旧备份、路由拆分和测试稳定。
2. 按 v1.3 PRD 拆分工作项底座实现任务。
3. v1.3 完成后再启动 v1.4，不提前做 Agent 自动调度。
4. v1.5 和 v1.6 可以提前细化设计，但实现必须依赖 v1.3-v1.4 的真实数据。
5. v2.0 在 v1.6 准备度报告通过后进入工程设计评审。
