# Nomos 商用化技术架构与开发任务拆解

> 状态：Draft
> 日期：2026-06-12
> 适用范围：C0 商用加固、C1 Local Pilot 试点包，并为 C2-C7 预留扩展边界。
> 目标读者：开发智能体、代码评审智能体、测试智能体、产品/项目经理。

## 0. 文档目标

本文件把商用化规划拆成可开发、可测试、可验收的工程任务。开发智能体拿到任务后，应能明确：

- 改哪些模块。
- 新增哪些数据字段。
- 暴露哪些 API。
- 前端需要哪些页面和状态。
- 必须跑哪些测试。
- 完成后交付什么证据。

## 1. 当前技术基线

### 1.1 应用形态

Nomos 当前是本地优先 Electron 桌面应用：

```text
Electron 主进程
  -> 启动本机 HTTP 后端
  -> renderer 通过 http://127.0.0.1:<port> 调 API
  -> JsonStore 写入 nomos-data.json
```

### 1.2 当前后端模块

| 模块 | 当前职责 |
|------|----------|
| `backend/server.js` | 创建 HTTP 服务、Host/Origin 校验、路由分发 |
| `backend/store.js` | JSON 持久化、迁移、备份、恢复、审计 |
| `backend/routes/projects.js` | 项目、阶段、验收、消息、交付物 |
| `backend/routes/org.js` | Skill、岗位、员工、组织健康度 |
| `backend/routes/flow.js` | 流程模板、流程实例、阶段回执、关口 |
| `backend/routes/agents.js` | Agent 列表和 Agent 目录 |
| `backend/routes/bridge.js` | 本地桥接、目录授权、Adapter 配置 |
| `backend/routes/system.js` | workspace、diagnostics、backup、execution、deployment |
| `backend/executor.js` | 本地 Agent 执行、确认令牌、取消、重试 |
| `backend/deployment.js` | 本地预览发布 |
| `backend/workflow.js` | 五阶段工作流状态机和 Agent 信封 |

### 1.3 C0 已知风险

当前测试暴露出路由拆分后的稳定性问题：

- 部分路由模块依赖未显式导入。
- 部分 handler 参数顺序与调用方不一致。
- 某些请求已经写响应后继续进入外层异常处理，出现 `Cannot write headers after they are sent to the client`。
- `/api/workspace`、`/api/agents`、组织和流程相关接口需要作为 C0 首要修复项。

## 2. 目标架构

### 2.1 商用化分层

```text
Renderer UI
  -> Onboarding / Settings / License / Support / Release widgets

Local API Layer
  -> routes/system.js
  -> routes/commercial.js
  -> routes/support.js

Domain Services
  -> SettingsService
  -> LicenseService
  -> SupportBundleService
  -> ReleaseChannelService
  -> RedactionService
  -> OnboardingService

Data Plane
  -> JsonStore
  -> nomos-data.json
  -> backups/
  -> support-bundles/
```

### 2.2 新增后端文件建议

| 文件 | 职责 |
|------|------|
| `backend/routes/commercial.js` | License、settings、onboarding API |
| `backend/routes/support.js` | 支持包列表、创建、下载 |
| `backend/commercial/license.js` | License 解析、验签、状态计算、功能开关 |
| `backend/commercial/settings.js` | 设置默认值、更新校验、版本通道校验 |
| `backend/commercial/onboarding.js` | 首次启动状态、样例初始化、试点目标 |
| `backend/support/redaction.js` | 敏感信息脱敏、路径摘要、字段黑名单 |
| `backend/support/support-bundle.js` | 生成支持包 manifest、diagnostics、audit sample |
| `backend/support/errors.js` | 最近错误记录和错误码映射 |

说明：C1 可以先不引入复杂类体系，但必须保持职责边界清晰。小函数模块优先，避免把所有逻辑塞进 `routes/system.js`。

### 2.3 前端模块建议

当前前端主要集中在 `renderer/app.js`。C1 可以继续单文件增量，但必须以清晰函数前缀组织：

| 函数前缀 | 职责 |
|----------|------|
| `renderOnboarding*` | 首次启动向导 |
| `renderSettings*` | 设置页 |
| `renderLicense*` | License 状态和导入 |
| `renderSupport*` | 诊断和支持包 |
| `api.commercial*` | 商用控制面 API |

若前端继续增长超过 2500 行，应在 C2 前拆分 renderer 模块。

## 3. 数据模型设计

### 3.1 数据版本

C1 建议将 `nomos-data.json` 版本从 v8 升到 v9c 或 v14。为了避免和 v1.3 的 `workItems` v9 冲突，建议采用：

| 字段 | 策略 |
|------|------|
| `version` | 产品核心数据版本，v1.3 仍使用 v9 |
| `commercialVersion` | 商用控制面版本，C1 使用 1 |

这样 C1 可以并行进入 v1.2.1，而不阻塞 v1.3 的核心数据迁移。

### 3.2 `settings`

```json
{
  "workspaceName": "Nomos Local Workspace",
  "customerId": "local",
  "releaseChannel": "pilot",
  "onboardingCompleted": false,
  "pilotGoal": {
    "scenario": null,
    "owner": null,
    "targetDate": null,
    "successCriteria": []
  },
  "diagnostics": {
    "includePathHash": true,
    "includeAuditSample": true
  },
  "createdAt": "2026-06-12T00:00:00.000Z",
  "updatedAt": "2026-06-12T00:00:00.000Z"
}
```

### 3.3 `license`

```json
{
  "status": "trial",
  "plan": "pilot",
  "licenseId": null,
  "customerName": null,
  "features": ["local_pilot", "support_bundle"],
  "releaseChannels": ["pilot"],
  "issuedAt": null,
  "expiresAt": null,
  "importedAt": null,
  "lastCheckedAt": "2026-06-12T00:00:00.000Z",
  "lastError": null
}
```

### 3.4 `supportBundles[]`

```json
[
  {
    "id": "uuid",
    "fileName": "nomos-support-2026-06-12T00-00-00.json",
    "reason": "manual",
    "redactionVersion": 1,
    "createdAt": "2026-06-12T00:00:00.000Z",
    "size": 12345
  }
]
```

### 3.5 迁移要求

`migrateData()` 必须保证：

- 缺失 `settings` 时补默认值。
- 缺失 `license` 时补 trial/missing 状态。
- 缺失 `supportBundles` 时补空数组。
- 旧备份 inspect/restore 后也能补齐商用字段。
- 迁移不得改变已有 `projects`、`agents`、`skills`、`roles`、`employees`、`flowTemplates`、`flowInstances`。

## 4. API 设计

### 4.1 Settings API

#### `GET /api/settings`

返回：

```json
{
  "data": {
    "workspaceName": "Nomos Local Workspace",
    "customerId": "local",
    "releaseChannel": "pilot",
    "onboardingCompleted": false,
    "pilotGoal": {},
    "diagnostics": {}
  }
}
```

#### `PATCH /api/settings`

请求：

```json
{
  "workspaceName": "客户试点工作区",
  "releaseChannel": "pilot",
  "diagnostics": {
    "includeAuditSample": true
  }
}
```

验收：

- 写入审计 `settings.update`。
- 不允许设置 License 未授权通道。
- 不允许写入任意对象字段污染数据结构。

### 4.2 License API

#### `GET /api/license`

返回当前 License 状态，不返回签名原文。

#### `POST /api/license/import`

请求：

```json
{
  "licenseText": "{...}",
  "confirm": true
}
```

验收：

- `confirm !== true` 返回 400。
- 无效 License 返回 400 且不覆盖旧 License。
- 有效 License 写入审计 `license.import`。

### 4.3 Onboarding API

#### `GET /api/onboarding`

返回是否完成、可用场景、样例初始化状态。

#### `POST /api/onboarding/complete`

标记完成或跳过。

#### `POST /api/onboarding/init-samples`

请求：

```json
{
  "scenario": "opc_project_delivery",
  "includeOrgDefaults": true,
  "includeFlowDefaults": true,
  "includeSampleProject": true,
  "confirm": true
}
```

验收：

- 必须显式确认。
- 幂等，不重复创建默认模板。
- 失败时不留下半初始化数据。

### 4.4 Support Bundle API

#### `GET /api/support/bundles`

列出历史支持包。

#### `POST /api/support/bundles`

请求：

```json
{
  "reason": "customer-support",
  "confirm": true
}
```

返回：

```json
{
  "data": {
    "fileName": "nomos-support-2026-06-12T00-00-00.json",
    "createdAt": "2026-06-12T00:00:00.000Z",
    "size": 12345
  }
}
```

验收：

- 必须显式确认。
- 文件写入 `support-bundles/`。
- 写入审计 `support.bundle.create`。
- 通过敏感字段扫描。

## 5. 安全与脱敏

### 5.1 敏感字段黑名单

支持包和诊断输出不得包含字段名匹配：

```text
token
tokenHash
confirmationToken
authorization
apiKey
secret
password
ANTHROPIC_AUTH_TOKEN
OPENAI_API_KEY
```

匹配不区分大小写。

### 5.2 路径处理

默认不导出完整用户路径。需要定位路径问题时，使用：

```json
{
  "pathHash": "sha256:...",
  "basename": "nomos-data.json"
}
```

### 5.3 本地 API 保护

C0 必须保持：

- Host 只允许 `127.0.0.1` 或 `localhost`。
- API Origin 必须与 Host 同源。
- C1 可追加本地 session nonce，但不作为 C0 阻断项。

| 阶段 | 当前架构预留 |

## 9. 开发完成定义

每个任务完成时，开发智能体必须提交：

- 变更摘要。
- 修改文件列表。
- 数据迁移说明。
- API 变更说明。
- 自动化测试结果。
- 手工验证步骤。
- 已知风险和未做事项。

没有测试证据的任务不得进入验收。

## 10. 代码实现约束

- 不引入数据库，C0-C1 继续使用 `JsonStore`。
- 不引入在线服务依赖，License 先做离线校验。
- 不改变现有项目、组织、流程的公开数据结构，除非有迁移测试。
- 不把 License 过期逻辑写入底层数据读取路径。
- 不在支持包中导出客户正文、Prompt 原文、完整本地路径或环境变量。
- 不把商用功能写成散落在各路由里的 if/else，必须有可测试 helper。

## 11. 验收顺序

```text
C0-T01 路由稳定
  -> C0-T02 冒烟测试
  -> C0-T03~T05 核心接口恢复
  -> C0-T06 脱敏
  -> C1-T01 数据迁移
  -> C1-T02~T05 后端控制面
  -> C1-T06~T07 前端控制面
  -> C1-T08 文档
  -> C1-T09 验收测试
```

任何上游 P0 未通过，下游任务只允许开发，不允许进入客户交付。
