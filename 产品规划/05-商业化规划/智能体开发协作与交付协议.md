# Nomos 智能体开发协作与交付协议

> 状态：Draft
> 日期：2026-06-12
> 用途：当 Nomos 的开发工作交给多个智能体执行时，统一任务输入、交付格式、测试证据、评审和验收规则。

## 0. 核心原则

Nomos 可以由多个智能体并行开发，但产品和质量不能并行失控。所有智能体必须遵守：

1. 先读相关文档，再改代码。
2. 任务必须小到可验收。
3. 所有数据结构变更必须有迁移和回退说明。
4. 所有接口变更必须有测试。
5. 所有高风险能力必须显式确认、审计和脱敏。
6. 没有证据的完成不算完成。

## 1. 角色分工

| 角色 | 职责 | 输出 |
|------|------|------|
| 产品/项目经理 | 定义范围、优先级、验收标准和发布门禁 | PRD、任务包、验收报告、发布判断 |
| 架构智能体 | 定义模块边界、数据模型、接口和迁移方案 | 技术方案、ADR、架构评审意见 |
| 后端智能体 | 实现 store、routes、domain service、测试 | 代码、迁移、API 测试 |
| 前端智能体 | 实现页面、交互、状态和空态 | UI 代码、手工验证截图/说明 |
| 测试智能体 | 补自动化测试、手工验收、故障注入 | 测试报告、缺陷清单 |
| 安全智能体 | 检查本地 API、命令执行、敏感信息和支持包 | 安全测试结果、修复建议 |
| 发布智能体 | 打包、校验、发布说明、回退包 | 安装包、校验值、发布清单 |

一个智能体可以承担多个角色，但交付物必须按角色输出。

## 2. 开发任务包格式

每个任务必须以如下格式交给开发智能体：

```markdown
## 任务 ID

例如：C0-T01

## 背景

说明为什么做、关联哪个版本/门禁。

## 范围

- 做什么
- 不做什么

## 相关文档

- PRD
- 架构文档
- 验收矩阵

## 主要文件

- 预计修改文件
- 预计新增文件

## 接口/数据模型

列出 API、字段、迁移要求。

## 验收标准

- 自动化测试
- 手工路径
- 错误场景

## 交付要求

- 变更摘要
- 测试结果
- 风险说明
```

没有任务 ID 的开发请求，不进入正式任务队列。

## 3. 分支和提交规范

| 类型 | 规范 |
|------|------|
| 分支 | `codex/<topic>` |
| 提交 | 中文或英文均可，但必须简短说明完整变更 |
| PR 标题 | `[codex] <变更摘要>` |
| PR 类型 | 默认 Draft，验收通过后再 Ready |
| 范围 | 一个 PR 只解决一个任务包或一组强相关任务 |

禁止把无关重构、格式化和功能混在一个任务包里。

## 4. 代码变更规则

### 4.1 后端

- 路由 handler 必须明确返回 `true/false` 或在写响应后立即 `return`。
- 不允许一个请求写两次响应。
- `readJson()` 错误必须返回可读 400。
- 所有写操作必须写审计。
- 所有危险操作必须有 `confirm === true`。
- 所有新增数据字段必须在 `migrateData()` 和 backup restore 路径验证。

### 4.2 前端

- 不做营销落地页，直接做可操作界面。
- 空态必须可解释。
- 错误提示必须展示用户可采取的下一步。
- 高风险操作必须二次确认。
- License 过期不得遮挡客户数据导出入口。

### 4.3 数据

- 数据迁移必须幂等。
- 迁移前后不得丢失旧字段。
- 新增数组默认 `[]`，新增对象默认结构完整。
- 不允许把 unknown 伪装成 0。

### 4.4 安全

- 任何支持包、日志、审计导出都必须脱敏。
- 不输出完整 Token、API Key、确认令牌、环境变量。
- 本地命令执行必须保留只读默认和写入二次确认。
- 不扩大默认目录授权。

## 5. 测试证据要求

每个开发任务至少提交以下测试证据之一：

| 任务类型 | 必需证据 |
|----------|----------|
| 路由/API | Node 自动化测试输出、curl/fetch 手工验证 |
| 数据迁移 | 旧数据 fixture 迁移前后摘要 |
| 前端交互 | 本地服务 URL、关键路径截图或操作记录 |
| 安全/脱敏 | 敏感字段 fixture 扫描结果 |
| 发布 | 安装包启动记录、SHA256、回退步骤 |
| 文档 | 链接检查、目录索引更新 |

对 C0/C1，`npm test` 是 P0 证据。若因已知基线问题无法全绿，必须列出失败用例、原因和阻断级别。

## 6. 交付回执格式

开发智能体完成任务后，必须按以下格式回复：

```markdown
## 完成范围

- ...

## 修改文件

- ...

## 测试结果

- `npm test`: pass/fail
- 其他测试：...

## 手工验证

1. ...

## 数据迁移

- 迁移版本：
- 回退方式：

## 风险和未做

- ...

## 建议验收路径

1. ...
```

如果没有这一段，项目经理不进行验收。

## 7. 验收流程

```text
开发智能体提交
  -> 测试智能体跑自动化和手工路径
  -> 安全智能体检查高风险项
  -> 产品/项目经理按验收矩阵签收
  -> 发布智能体进入打包或归档
```

C0/C1 的验收顺序必须遵守：

1. 先修测试基线。
2. 再做商用控制面。
3. 再做前端入口。
4. 最后做发布包和客户文档。

## 8. 任务状态定义

| 状态 | 定义 |
|------|------|
| Draft | 任务描述中，还不能开发 |
| Ready | 范围、验收、相关文档齐备 |
| In Progress | 智能体开发中 |
| Blocked | 缺依赖或验收条件无法满足 |
| Review | 已提交，等待测试/评审 |
| Accepted | 验收通过 |
| Rejected | 验收失败，需要返工 |
| Deferred | 明确延期，不进入本版本 |

## 9. 缺陷分级

| 级别 | 定义 | 处理 |
|------|------|------|
| S0 | 数据丢失、敏感信息泄露、无法启动 | 立即阻断发布 |
| S1 | 主链路不可用、测试大面积失败 | 当前里程碑阻断 |
| S2 | 单功能失败但有绕行 | 进入本迭代修复 |
| S3 | 文案、空态、低频体验问题 | 可排后续 |

## 10. C0-C1 首批任务包

| ID | 名称 | 优先级 | 依赖 | 交付智能体 |
|----|------|--------|------|------------|
| C0-T01 | 路由稳定性修复 | P0 | 无 | 后端 |
| C0-T02 | API 冒烟测试 | P0 | C0-T01 | 测试 |
| C0-T03 | workspace/agent/org/flow 接口恢复 | P0 | C0-T01 | 后端 |
| C0-T04 | 诊断脱敏基础 | P0 | C0-T01 | 安全/后端 |
| C0-T05 | C0 测试报告和发布门禁 | P0 | C0-T02~T04 | 测试/文档 |
| C1-T01 | 商用数据模型迁移 | P0 | C0 全部 | 后端 |
| C1-T02 | License/Settings API | P0 | C1-T01 | 后端 |
| C1-T03 | Support Bundle API | P0 | C1-T01 | 后端/安全 |
| C1-T04 | 首次启动向导 | P1 | C1-T01 | 前端 |
| C1-T05 | License/Support UI | P1 | C1-T02~T03 | 前端 |
| C1-T06 | 用户手册和实施手册更新 | P1 | C1-T04~T05 | 文档 |

## 11. 禁止事项

- 禁止在没有迁移测试的情况下修改数据结构。
- 禁止把客户数据上传到外部服务做诊断。
- 禁止把 License 过期做成数据锁死。
- 禁止绕过确认直接执行本地写入任务。
- 禁止在支持包中包含 `.env`、shell 环境变量、完整 Prompt、Token。
- 禁止开发智能体自行扩大版本范围。

## 12. 项目经理验收口径

项目经理只按文档验收，不按“看起来能跑”验收。验收时优先看：

1. 是否满足任务 ID 的范围。
2. 是否通过 P0 自动化测试。
3. 是否提供手工路径证据。
4. 是否保护旧数据和备份恢复。
5. 是否更新相关文档。
6. 是否留下明确风险。

任何一项缺失，状态保持 `Review` 或 `Rejected`。
