# PRD：Workflow 引擎升级

## 背景

Nomos v1.0.1 的工作流是一个固定的五阶段交付链路：

> 提出目标 → 总管拆解 → PRD → 本地开发 → 测试 → 预览发布 → 人工验收

这个链路为"Agent 帮你开发一个项目"这个场景设计得很好。但产品理念文档定义的 Workflow 要远比这复杂：

1. **五级分层**：L1 价值流 → L2 阶段 → L3 任务 → L4 步骤 → L5 节点
2. **碳硅节点标注**：每个节点明确碳/硅/碳硅属性
3. **事件驱动**：市场信号、客户行为、数据异常、时间触发都能启动或推进工作流
4. **动态编排**：阶段可跳转、可并行、可条件分支

v1.2 的流程管理模块解决了"流程模板从哪来"的问题，本 PRD 解决"流程跑起来"的问题。

## 用户与场景

### 主要用户

| 用户 | 特征 | 核心诉求 |
|------|------|---------|
| 流程 Owner | 定义了流程模板，需要它真正跑起来 | 流程的每个阶段能自动派发到正确的角色或 Agent |
| 数字员工 | 被指派到流程的某个节点上执行任务 | 清楚知道自己该做什么、按什么标准做、做完后怎么交接 |
| 项目经理 | 需要监控流程运行状态 | 看到流程运行到哪个阶段/任务/节点，哪里阻塞了 |

### 典型场景

**场景一：LTC 流程自动运行**

一个销售项目绑定了"LTC 轻量版"流程模板后：

1. **线索阶段**（硅节点）：Agent 自动从 CRM 导出线索并去重评分
2. **线索分配**（碳硅节点）：Agent 推荐分配方案，销售主管确认
3. **商机评估**（碳硅节点）：Agent 生成客户画像和竞品分析，销售判断可行性
4. **方案设计**（碳节点）：销售 + 方案经理协作
5. **报价审批**（碳硅节点）：Agent 校验折扣权限，主管审批
6. **合同签订**（碳节点）：法务签字
7. **交付跟踪**（硅节点）：Agent 监控进度，异常告警
8. **开票回款**（硅节点）：Agent 跟踪回款状态
9. 每个阶段之间有关口评审，通过后自动推进到下一阶段

**场景二：碳硅节点自动调度**

流程运行到一个硅节点时：
1. 系统根据节点绑定的 Agent（如 Claude Code）自动派发任务
2. Agent 执行完毕后提交结构化回执
3. 系统校验回执是否满足准出标准
4. 满足则自动推进到下一阶段，不满足则标记异常并通知人类

**场景三：事件触发流程推进**

合同回款 Workflow 中：
1. Agent 监控每笔款项到账状态
2. 正常到账：自动确认，更新记录
3. 逾期 7 天未到账：触发事件，Agent 自动发送催款提醒
4. 逾期 14 天未到账：升级为碳节点，推送到财务负责人工作台

## 要解决的问题

1. **工作流是固定的**：当前五阶段是硬编码的，不能配置为其他流程
2. **节点不分碳硅**：当前没有碳/硅/碳硅的概念，所有节点都是人工驱动的
3. **不支持事件驱动**：工作流只能由人工点击推进，不能由外部事件触发
4. **不支持并行和分支**：阶段只能串行执行

## 成功指标

| 指标 | 当前基线 | 目标 |
|------|---------|------|
| 硅节点自动执行率 | 0% | 硅节点 90% 以上自动完成并回执 |
| 碳硅节点人工介入率 | N/A | 碳硅节点 80% 以上 Agent 预审后人工一次确认通过 |
| 流程端到端完成率 | N/A | 绑定流程的项目 60% 以上端到端完成 |
| 平均关口评审耗时 | N/A | 硅评审 < 1 分钟，碳硅评审 < 10 分钟，碳评审 < 24 小时 |

## 本版范围

### 五级分层工作流

- L1 价值流：从流程模板继承（v1.2 已定义）
- L2 阶段：从流程模板继承，增加阶段状态机
- L3 任务：阶段内的可执行任务单元，支持并行
- L4 步骤：任务的执行步骤序列
- L5 节点：最小调度单元，标注碳/硅/碳硅属性

### 碳硅节点调度

- 碳节点：推送待办到工作台，设定截止时间，超时升级
- 硅节点：自动派发给绑定的 Agent，执行后回收结构化回执
- 碳硅节点：Agent 先执行预审，生成建议/方案/分析，推送给人类做最终决策

### 事件驱动

- 内部事件：阶段完成、回执提交、关口评审通过
- 外部事件：HTTP Webhook 触发（v2.0 只做入口，不做完整的 Webhook 管理界面）
- 时间事件：定时触发（如每日回款检查）
- 事件 → 阶段推进/通知/升级的映射配置

### 动态编排

- 条件分支：根据节点输出决定走哪条路径
- 并行执行：多个独立任务同时派发
- 阶段跳转：关口评审不通过时跳回指定阶段
- 异常处理：节点失败时的重试、升级、跳过策略

### 流程运行监控

- 流程实例状态面板：当前阶段、活跃节点、阻塞节点、已完成节点
- 节点执行日志：每个节点的执行时间、执行者、输入输出
- 流程热力图：各阶段平均耗时、瓶颈识别

## 不做范围

- 不做 SLA 自动计时和超时升级的完整引擎（只做简单超时通知）
- 不做跨流程编排和子流程调用
- 不做流程版本管理和 diff
- 不做流程仿真
- 不做复杂的条件表达式引擎（条件分支用简单的状态值匹配）
- 不做 Webhook 管理界面（只提供 API 入口）

## 交互流程

### 流程运行

```
项目绑定流程模板 →
  系统根据模板创建 L1-L2 结构 →
    第一阶段启动 →
      遍历该阶段的 L3 任务 →
        每个任务遍历 L4 步骤 →
          每个步骤检查 L5 节点类型 →
            [硅节点] 自动派发 Agent → 回收回执 →
            [碳节点] 推送待办 → 等待人工完成 →
            [碳硅节点] Agent 预审 → 推送人工决策 →
      所有任务完成 → 提交阶段关口评审 →
        [通过] 推进到下一阶段 →
        [不通过] 返回当前阶段或指定阶段
      所有阶段完成 → 流程结束
```

## 数据与权限

### 数据模型扩展

```
flow-instance: {
  id, projectId, templateId,
  status: 'running' | 'paused' | 'completed' | 'failed',
  currentStageId,
  stages: [{
    id, templateStageId, name, order,
    status: 'pending' | 'running' | 'completed' | 'blocked',
    tasks: [{
      id, name, status,
      steps: [{
        id, name, order, status,
        node: {
          type: 'carbon' | 'silicon' | 'hybrid',
          executor: { type, employeeId?, agentId? },
          input: {},
          output: {},
          startedAt, completedAt,
          receipt: {}
        }
      }]
    }],
    gate: {
      status, review: { reviewer, comment, reviewedAt }
    }
  }],
  eventSubscriptions: [{
    eventType, source, action, targetStageId
  }],
  startedAt, completedAt
}
```

### 存储方式

沿用当前单一 `nomos-data.json` 文件持久化方式，不新增独立 JSON 文件。在 `data` 对象中新增 `flowInstances` 数组，现有 `projects[]` 中的 `flowStages` 升级为 `flowInstanceId` 引用。通过 `migrateData()` 版本升级自动补全 `flowInstances: []`，保证备份、恢复和迁移仍在同一数据文件内完成。

### 与 Agent 路由的衔接

`agent-router.js` 的路由逻辑扩展：
- 当前：根据阶段 key 选择 Agent
- v2.0：根据节点类型、节点绑定的角色、Agent 可用性综合选择
  - 硅节点 → 自动选择绑定的 Agent
  - 碳硅节点 → 自动选择绑定的 Agent 做预审，推送人类做终审
  - 碳节点 → 不路由到 Agent，只推送到工作台

### 与工作流状态机的衔接

`workflow.js` 的状态机扩展：
- 当前：五阶段线性状态机
- v2.0：支持流程模板定义的任意阶段序列，支持分支、并行、跳转

## 验收标准

### 自动化测试

- L2-L5 分层创建和遍历测试
- 碳节点推送测试
- 硅节点自动派发和回执回收测试
- 碳硅节点预审 + 人工终审测试
- 条件分支路径选择测试
- 并行任务执行和等待测试
- 关口评审状态流转测试
- 异常处理（节点失败、重试、升级）测试
- 事件触发流程推进测试

### 手工验收

- 用"LTC 轻量版"流程模板创建项目，走完完整流程
- 至少包含 2 个硅节点自动执行、1 个碳硅节点预审终审、1 个碳节点人工处理
- 关口评审不通过时正确返回
- 流程运行监控面板正确显示状态

## 风险与回退

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| 五级分层增加复杂度，用户不会配置 | 流程模板使用率低 | 提供 L1-L2 即可用的简化模式，L3-L5 可选 |
| 硅节点 Agent 执行失败率高 | 流程阻塞 | 失败重试 + 超时升级到碳节点 |
| 事件驱动引入不确定性 | 流程状态难以预测 | 事件只做触发入口，不改变核心状态机逻辑 |

## 技术方案概要

### 重构 workflow.js

当前的 `workflow.js` 是一个 525 行的五阶段状态机。v2.0 需要重构为通用的工作流引擎：

1. **引擎核心**：接收流程模板，生成流程实例，驱动节点执行
2. **调度器**：根据节点类型选择执行策略（碳/硅/碳硅）
3. **状态管理**：维护流程实例状态，支持分支和并行
4. **事件处理器**：接收事件，匹配订阅规则，触发流程推进

### 重构 agent-router.js

从"阶段路由"升级为"节点路由"：
- 输入从 `stageKey` 变为 `node`（包含类型、角色、绑定 Agent）
- 输出增加 `autoDispatch` 标志（硅节点自动派发，碳节点不派发）

### 新增 flow-engine.js

独立的工作流引擎模块，职责：
- 流程实例生命周期管理
- 节点调度策略执行
- 关口评审状态机
- 事件触发和匹配
