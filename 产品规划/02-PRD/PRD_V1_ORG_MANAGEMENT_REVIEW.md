## 一、PRD 质量评估

**整体评价：需补充。**

PRD V1.0 在场景覆盖、四层模型引用和需求优先级上做得不错，但存在 **7 个关键缺失** 和 **5 个范围模糊点**，不补充则架构师无法直接进入技术设计。

### 做得好的部分

1. **场景驱动**：三个典型场景（OPC 创业者、小微团队、数字员工上岗）清晰具体，用户画像明确
2. **四层模型引用**：明确引用了信息架构的四层模型，方向正确
3. **六步拆分策略**：前三步/后三步的版本拆分合理，避免了 v1.1 范围蔓延
4. **成功指标有基线**：虽然部分指标为运营指标（见下文），但至少有方向性目标
5. **不做范围有意识**：列出了不做清单，比完全没有边界好

## 二、发现的问题与缺失点

### 关键缺失（必须在开发前补齐）

| # | 问题 | 影响 | 增强措施 |
|---|------|------|---------|
| 1 | **Technical Adapter 未作为一级实体建模** | 信息架构四层模型的第四层缺失，硅基员工的 adapterId 无处可指，数字员工"双重身份"无法实现 | 新增 Technical Adapter 管理章节，明确 Adapter 来源为现有 `data.agents` + `data.agentAdapters` |
| 2 | **数字员工草稿无数据模型** | 前三步的配置数据无处存放，架构师无法设计 API 和存储 | 在 employee 模型中嵌入 `digitalEmployeeDraft` 完整结构，含状态机和每步的具体字段 |
| 3 | **存储方案与现有代码冲突** | PRD 提出三个独立 JSON 文件，但 store.js 使用单一 `nomos-data.json` | 修正为沿用单一文件，在 `data` 对象中新增三个数组字段，通过 `migrateData()` v6→v7 升级 |
| 4 | **六步前三步缺少配置项细节** | "配置 Skill 等级"具体配置什么？"绑定知识库"但无知识库模块？ | 为每步定义具体配置项、数据结构和范围边界（入职培训仅记录引用，不做消费） |
| 5 | **与现有代码的兼容性未考虑** | `agents`、`agentAdapters` 已有数据结构，硅基员工如何引用？API 风格如何统一？ | 新增"与现有代码的兼容性"章节，逐一对齐现有数据结构；新增 API 路由设计 |
| 6 | **岗位-流程矩阵有前向依赖** | `flowMatrix` 引用 `flowId`，但流程管理是 v1.2 的范围 | v1.1 用 `flowNotes`（自由文本）过渡，`flowMatrix` 预留但不在 UI 暴露 |
| 7 | **验收标准不可度量** | "走通"不是测试标准，成功指标是运营指标不是功能指标 | 重写验收标准：自动化测试含具体 HTTP 状态码和断言，手工验收含四条可执行路径 |

### 范围模糊点（已澄清）

| # | 模糊点 | 澄清 |
|---|--------|------|
| 1 | 入职培训"绑定企业知识库" | v1.1 无知识库模块，仅记录引用文本（URL/路径），不做内容消费 |
| 2 | 师父带教"定义工作流程" | v1.1 的 SOP 为自由文本，不做与 Workflow 引擎的结构化关联 |
| 3 | "岗位缺口提示"依赖流程模板 | v1.1 无流程数据，岗位缺口简化为"空岗位族提示"，原功能移至 v1.2 |
| 4 | 硅基员工的 Adapter 配置 | adapterConfig 过于模糊，改为引用现有 `data.agentAdapters` 中的配置 |
| 5 | 默认岗位族预设的 CRUD 规则 | 预设岗位 `isDefault: true`，不可删除仅可隐藏 |

### 数据模型增强

| 模型 | 新增字段 | 理由 |
|------|---------|------|
| skill | `source`, `evidence[]` | 对齐产品理念"三种来源"和 SFIA"能力证据化" |
| role | `family`, `type`, `isDefault`, `flowNotes`, `skillLevelOverrides` | 对齐信息架构的岗位族/岗位类型定义，v1.1 流程过渡方案 |
| employee | `agentId`, `digitalEmployeeDraft` (完整结构) | 引用现有 Agent，草稿状态机 |
| (新增) | Technical Adapter 视图 | 从现有 `agents` + `agentAdapters` 聚合，不新增存储 |

## 三、对架构师的关键提示

### 1. 数据存储：不要新建文件

v1.1 组织数据**必须**放入 `nomos-data.json`，通过 `migrateData()` 版本升级（v6→v7）自动补全。不要新建 `skills.json` 等独立文件——这与 `JsonStore` 的设计哲学冲突（单文件原子写入、备份恢复、事务性保存）。

### 2. Agent 引用：不要重复创建

硅基员工的 `agentId` 直接引用 `data.agents[].id`，`adapterId` 引用 `data.agentAdapters` 的 key。不要为组织模块新建一套 Agent 实体——那会导致数据不一致。

### 3. flowMatrix 是 v1.2 的事

v1.1 中 `role.flowMatrix` 在数据模型中预留（空数组），但 UI 不暴露。v1.1 用 `role.flowNotes` 做自由文本的流程关联描述。建议 `flowNotes` 设计时有格式约定（如"LTC/线索管理/R"），方便 v1.2 脚本化迁移。

### 4. 数字员工草稿是嵌入字段

`digitalEmployeeDraft` 嵌入 `employee` 模型中，不独立存储。草稿与员工身份绑定——一个硅基员工从创建时就有草稿，转正后草稿归档。不要设计独立的 drafts 集合。

### 5. 默认模板生成是 API 调用

7 大岗位族的预置数据通过 `POST /api/org/init-defaults` 按需生成，不在 `createDefaultData()` 中硬编码。原因：用户可能从 v1.0.1 升级到 v1.1 时不想覆盖已有组织数据。

### 6. 前端 API 层沿用 app.js 模式

在 `renderer/app.js` 的 `api` 对象中新增组织相关方法（`skills()`, `createSkill()` 等），与现有的 `projects()`, `createProject()` 风格一致。

### 7. 关注 v1.2 的数据迁移准备

v1.2 流程管理上线时需要：
- `skill.applicableFlows` 从 `string[]` 迁移为 `flowId[]`
- `role.flowNotes` 迁移为 `role.flowMatrix`
- `project` 关联 `role.flowMatrix` 中的流程

v1.1 的数据设计要为这些迁移留好空间。
