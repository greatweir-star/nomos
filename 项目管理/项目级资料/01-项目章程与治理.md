# Nomos 项目章程与治理

> 状态：生效  
> 生效日期：2026-06-21  
> 适用范围：Nomos 全生命周期

## 1. 项目使命

Nomos 是以流程为核心的本地优先企业管理操作系统。流程承载企业经验，岗位和碳硅员工是执行资源，项目将已发布流程实例化并形成可派发、可验收、可审计的工作闭环。

## 2. 治理目标

- 每个版本只有一个可追踪的范围基线。
- 产品需求、技术实现、测试证据和发布结论可双向追踪。
- 前端、后端、测试可基于稳定合同并行开发。
- 任何高风险变更均有负责人、原因、影响、回退方案和验收证据。
- 历史材料保留，但不得成为活动版本的隐性需求。

## 3. 角色与责任

| 角色 | 本项目负责人 | 核心责任 | 必须签署的出口 |
| --- | --- | --- | --- |
| 产品经理 | Codex（主代理） | 用户问题、范围、交互、需求优先级、产品验收 | PRD、范围基线、UAT |
| 研发项目经理 | Codex（主代理） | 计划、WBS、依赖、风险、变更、交付节奏 | 版本计划、里程碑、发布建议 |
| 架构师 | Codex（主代理） | 架构边界、领域模型、API/数据合同、ADR、技术验收 | 架构基线、接口冻结、技术门禁 |
| 前端开发 | 后续指定智能体 | 页面、交互、状态和前端自动化测试 | 前端任务包、UI 验收证据 |
| 后端开发 | 后续指定智能体 | 领域服务、API、数据迁移、连接器和后端测试 | API 合同、迁移报告、集成测试 |
| 测试 | 后续指定智能体 | 测试设计、合同测试、E2E、回归和发布判断 | 测试报告、缺陷清单、发布结论 |

## 4. 标准生命周期

```text
立项 → 需求基线 → 架构基线 → 计划与任务拆分 → 开发
    → 联调 → 系统测试 → 产品验收 → 发布评审 → 发布与复盘
```

### G0 立项门禁

- 版本目标、用户价值、范围和非范围明确。
- 有唯一核心 PRD。
- 角色、负责人和决策机制明确。

### G1 需求门禁

- 每项需求有稳定 ID、用户场景、业务规则和可测试验收条件。
- 产品术语与对象关系无冲突。
- P0/P1/P2 优先级明确。

### G2 架构门禁

- 模块边界、数据所有权、API 合同、状态机和迁移路径明确。
- 开放决策已关闭或有默认方案。
- 前后端可以基于合同独立实现。

### G3 开发就绪门禁

- 任务粒度不超过 1–3 个工程日。
- 每项任务有输入、输出、依赖、验收和回退。
- 测试用例在开发开始前建立。

### G4 发布门禁

- P0/P1 用例通过，P0/P1 缺陷为 0。
- 数据迁移、备份恢复和安全检查通过。
- 产品经理、架构师、测试给出一致发布结论。

## 5. 需求和变更控制

- 版本基线后新增需求必须提交变更记录，不允许口头插入。
- 变更必须说明：背景、收益、影响模块、工期影响、测试影响和回退方式。
- 影响数据模型、公开 API、安全边界或里程碑的变更必须形成 ADR。
- P0 缺陷可直接进入当前迭代，但必须补齐缺陷记录和回归用例。
- 非阻断增强进入候选池，不默认扩大当前版本。

## 6. 完成定义

一项任务只有同时满足以下条件才可标记完成：

- 需求验收条件已满足。
- 代码或文档已进入指定目录，未留下私有临时依赖。
- 单元/集成/合同测试通过。
- 错误态、空态、权限态和恢复态已处理。
- 数据、接口或用户行为变化已更新对应文档。
- 无未声明的风险、占位数据和伪造状态。
