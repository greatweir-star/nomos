# Nomos V0.0.3 版本 PRD

> 状态：Baseline  
> 上游核心逻辑：`产品开发/nomos-desktop/docs/NOMOS-PRD.md`（0.3 Draft）  
> 本文用途：把完整核心逻辑收敛为可交付版本范围；不替代上游需求细节。

## 1. 版本问题

现有产品已经具备项目、流程、Agent、组织和工作项雏形，但对象边界混合、演示数据与真实数据并存、派发直接依赖 Agent ID，尚不能稳定表达“流程按岗位调度碳硅员工并形成可验收证据链”。

## 2. 目标用户

| 主要角色 | 本版必须完成的任务 |
| --- | --- |
| 组织 Owner | 查看真实控制台、审批权限申请、处理关键验收 |
| 组织管理员 | 建立 Skill/岗位，接入连接，实例化和管理员工 |
| 流程 Owner | 发布软件开发流程版本，配置岗位槽位和验收标准 |
| 项目 Owner | 创建项目、启动流程、确认派发、查看进展和结果 |
| 验收员工 | 对回执及交付物执行通过、驳回和返工 |
| IT 管理员 | 在设置中确认连接可达、可管理和健康状态 |

## 3. 北极星链路

```text
保存可管理连接
→ 基于岗位实例化硅基员工
→ 发布软件开发流程版本
→ 创建项目并快照流程
→ 生成带岗位要求的工作项
→ 推荐员工并确认派发
→ 接收结构化回执
→ 碳基员工验收或返工
→ 控制台聚合真实运行数据
```

## 4. P0 范围

### P0-A 信息架构和真实状态

- 一级菜单：控制台、组织、能力池、流程、派发、项目、设置。
- Agent 集成移入 `设置 / Agent 集成`。
- 生产模式不得生成虚构员工、负载、流程、告警、回执和更新时间。
- 样例模板只能由用户主动导入，并带“模板/样例”标识。

### P0-B 技术连接

- 支持 Alice、Codex、Claude Code、Kimi 的发现、检测、命名、保存、禁用和重检。
- OpenClaw 按普通连接器占位，不自动安装或启动网关。
- 连接只表达“可达 + 可管理”，不管理智能体执行目录、命令权限和沙箱。
- 凭据不进入 JSON、日志、审计和备份。

### P0-C 组织与员工

- Skill 与 Position 可创建、编辑、停用并保护引用。
- 碳基员工可身兼多岗。
- **V0.0.3 决策：每个硅基员工只绑定一个主岗位和一个独立 sessionKey。** 同一 ConnectionProfile 可实例化多个硅基员工。
- 创建硅基员工时快照岗位技能、职责和验收标准并物化提示词。
- 未通过入职检查、连接异常、暂停或离职的员工不得进入路由候选。

### P0-D 流程与项目

- 第一条黄金模板为“软件需求到交付”：需求澄清、产品设计、技术方案、开发实现、代码评审、测试验证、发布验收。
- FlowDefinition 支持草稿；FlowVersion 发布后不可修改。
- 节点通过 PositionSlot 声明岗位需求，不直接绑定供应商。
- 项目启动时快照 FlowVersion；模板后续变化不影响运行实例。
- 每个岗位槽位生成一个 WorkItem，避免一个工作项多个责任人。

### P0-E 派发、回执和验收

- 路由先过滤：员工状态、连接状态、岗位、项目范围、容量；再排名。
- 派发预览展示候选、岗位、连接、负载、理由和权限缺口。
- 确认派发必须幂等；重复请求不得启动第二次执行。
- Receipt 与 Acceptance 分离：智能体完成不等于节点验收通过。
- 返工必须携带原工作项、原回执、验收意见和新 attempt。

### P0-F 数据、迁移和发布

- 新领域使用 SQLite 和显式 migration；旧 v9 JSON 先 dry-run，再由用户确认迁移。
- 迁移失败不得修改旧文件；迁移前创建保护副本。
- 备份、检查、恢复和恢复前保护快照可闭环。
- 保持 Electron 安全基线和 loopback/Origin 校验。

## 5. P1 范围

- PermissionRequest：岗位外管理权限申请、Owner 审批、有效期、撤销和审计。
- 批量派发风险摘要。
- 控制台异常聚合、超时提示和连接容量视图。
- 用户主动导入软件开发岗位包和流程模板。
- 外观、密度、语言和基本辅助功能设置。

## 6. 明确不做

- 远程 Gateway、多机同步和多人实时协作。
- SaaS、多租户、SSO、计费和模板市场。
- 由 Nomos 管理智能体执行目录、命令、网络权限或运行沙箱。
- 全量华为 16 个一级流程；本版只交付软件开发黄金流程。
- 回执驱动的 Skill 自动评级。
- 无人工确认的高风险自动派发。

## 7. 关键业务规则

1. ConnectionProfile 不能被直接派发，Employee 才是候选人。
2. 一次 WorkItem 派发必须记录 `actingPositionId`。
3. 有效管理权限按本次 `actingPositionId` 计算，再叠加有效 PermissionRequest；不采用多岗位权限无条件并集。
4. 发布后的 FlowVersion 不可变。
5. Receipt 只能陈述执行事实；Acceptance 决定业务是否通过。
6. 任何聚合数字都必须能下钻到真实对象。
7. 软删除对象保留历史引用，不允许破坏证据链。

## 8. 核心用户旅程验收

### Journey 1：首个连接与员工

IT 管理员在 5 分钟内保存一个可管理 Codex 连接；组织管理员以该连接分别创建“前端工程师”和“测试工程师”，两个员工拥有不同 sessionKey、岗位快照和状态。

### Journey 2：流程项目启动

流程 Owner 发布黄金流程；项目 Owner 创建项目并快照该版本；系统为每个岗位槽位生成独立工作项。

### Journey 3：完整交付闭环

项目 Owner 选择推荐员工、确认派发；系统收到结构化回执后进入待验收；验收员工可通过或返工，所有状态和证据在重启后保持一致。

### Journey 4：异常恢复

连接离线后相关员工不可调度；已有历史不丢失；连接恢复并重检后员工重新进入候选。

## 9. 产品成功指标

- 首个 ConnectionProfile 保存成功率 ≥ 90%，中位时长 ≤ 5 分钟。
- 首位硅基员工入职完成率 ≥ 80%。
- 黄金流程项目首次跑通率 ≥ 70%。
- 确认派发成功率 ≥ 95%，重复执行率为 0。
- 待验收工作项均可追踪 Receipt 与 Acceptance。
- 生产数据虚构项为 0，P0/P1 数据泄露缺陷为 0。

## 10. 开放项处理

| 项目 | V0.0.3 决策 |
| --- | --- |
| 数字员工扩展培训/带教 | 保留为后续扩展；本版四步向导完成到入职检查 |
| 人力资源流程 | 只做岗位模型参考，不作为本版可运行模板 |
| 审批人 | 单机版由 Owner 审批并完整留痕 |
| 碳基身份来源 | 手工创建，不与登录账号合并 |
