# Nomos 产品开发方法论与流程

版本：v0.1  
适用范围：Nomos 从当前 MVP 到未来几十个、上百个版本的持续迭代开发。  
核心目标：方向不跑偏，节奏不断档，质量不失控，知识不丢失。

---

## 1. 设计原则

### 1.1 方向先于功能

任何开发任务都必须能回答三个问题：

1. 它服务 Nomos 的哪个产品命题？
2. 它改善哪条端到端价值流？
3. 它让“人 + Agent + Workflow”的协同更清晰，还是更混乱？

不能回答这三个问题的功能，先进入 `产品规划\02-PRD` 或 `产品规划\03-版本规划`，不要直接进入开发。

### 1.2 小步快跑，但每步都可验收

Nomos 采用“可发布增量”而不是“堆功能半成品”。每一轮迭代结束时，必须至少产出其中之一：

- 可运行功能
- 可验证原型
- 可复用基础设施
- 可关闭风险的实验结论

### 1.3 双轨并行：探索和交付同时进行

产品探索和产品交付分成两条轨道：

- 探索轨：研究用户、流程、问题、方案和风险，决定“做什么、为什么做”。
- 交付轨：实现、测试、发布和复盘，决定“怎么做、做到什么标准”。

探索轨至少领先交付轨 1 个迭代周期，避免开发团队拿到未经验证的模糊需求。

### 1.4 参考源码优先

接到新的开发任务后，先查 `参考源码`。优先学习可复用的协议、结构、错误处理、测试方式和边界设计，再决定 Nomos 自己的实现。

### 1.5 文档是系统的一部分

PRD、设计决策、测试报告、发布说明不是“附属材料”，而是系统的组织记忆。没有文档沉淀的版本，不算完整版本。

## 2. 方法论来源与取舍

Nomos 不直接照搬某一种流程，而是组合以下实践：

- Scrum：使用 Sprint Goal、Product Backlog、Sprint Review、Retrospective 等机制，保证每轮迭代有目标、有验收、有复盘。
- Shape Up：引入“成形任务”和“投入胃口”，避免需求无限膨胀；重要功能先写 Pitch，再决定是否下注。
- Dual-track Agile：把产品发现和开发交付并行推进，减少拍脑袋开发。
- DORA / DevOps：用交付速度和稳定性指标监控工程健康，而不是只看“写了多少功能”。
- RFC / ADR：重大技术和产品决策留下可追溯记录。

Nomos 的取舍：

- 不做重型 Scrum，不让仪式压过产出。
- 不做无限 Backlog，不让需求池变成垃圾场。
- 不追求每次都大版本发布，优先保证每轮都有可验收增量。
- 不用指标考核个人，指标只用于发现系统瓶颈。

## 3. 四层节奏

### 3.1 年度产品方向

周期：半年到一年。

产物：

- 产品愿景
- 北极星指标
- 年度主题
- 关键用户画像
- 主要价值流地图

存放位置：

```text
产品规划\00-产品理念
产品规划\03-版本规划
```

Nomos 当前北极星建议：

> 用户能用 Nomos 把一个端到端流程交给“人 + Agent + Workflow”协同运行，并稳定得到可追踪、可验收、可复盘的结果。

### 3.2 季度版本规划

周期：8 到 12 周。

目标：确定一个阶段性产品主题，例如：

- Agent 接入与路由
- Workflow 引擎
- 组织记忆
- Skill 体系
- 发布与权限

产物：

- 版本目标
- 版本范围
- 不做清单
- 风险清单
- 验收标准

存放位置：

```text
产品规划\03-版本规划
```

### 3.3 双周开发迭代

周期：建议 2 周一轮。

每轮包含：

- 迭代计划
- 开发实现
- 自动化测试
- 手工验收
- 版本小结
- 下轮待办整理

存放位置：

```text
产品开发\nomos-desktop
产品开发\测试用例
产品开发\测试报告
产品开发\中间数据
```

### 3.4 发布节奏

建议：

- 修复版：随时发布，版本号如 `1.0.2`。
- 小版本：2 到 4 周发布一次，版本号如 `1.1.0`。
- 大版本：完成一组核心能力后发布，版本号如 `2.0.0`。

正式产物存放：

```text
产品发布\vX.Y.Z
```

## 5. 需求进入开发的门禁

一个需求进入开发前，必须满足以下条件。

### 5.1 问题清楚

必须写清楚：

- 用户是谁
- 当前痛点是什么
- 不解决会怎样
- 成功后用户行为会发生什么变化

### 5.2 价值明确

至少命中一个价值维度：

- 降低用户操作成本
- 提升 Agent 执行成功率
- 提升流程可追踪性
- 降低发布或运行风险
- 沉淀组织记忆
- 改善产品体验

### 5.3 范围可控

必须写清楚：

- 本轮做什么
- 本轮不做什么
- 最小可验收版本是什么
- 超出范围时如何砍掉

### 5.4 验收可测

必须提前定义：

- 自动化测试标准
- 手工验收步骤
- 失败回退方式
- 是否需要更新说明书

## 6. 需求分级

### L0 产品命题

例如：

> Nomos 要成为流程驱动型智能操作系统。

位置：

```text
产品规划\00-产品理念
```

### L1 版本主题

例如：

> v1.2 完成 Workflow 状态机和阶段回执体系。

位置：

```text
产品规划\03-版本规划
```

### L2 能力模块

例如：

- Agent 路由
- Alice 派发
- 本地备份恢复
- Workflow 阶段验收

位置：

```text
产品规划\02-PRD
产品开发\测试用例
```

### L3 开发任务

例如：

- 修复按钮无响应
- 增加恢复前保护快照
- 将 `heliu-data` 改为 `nomos-data`

位置：

```text
产品开发\nomos-desktop
```

## 7. 迭代流程

### 7.1 迭代开始

输入：

- 上轮复盘
- 当前版本规划
- PRD / Pitch
- 风险清单

输出：

- 本轮目标
- 本轮任务清单
- 本轮不做清单
- 验收标准

原则：

- 每轮只允许 1 个主目标。
- 任务可以多个，但都必须服务主目标。
- 发现主目标错误时，宁可中止重排，也不要硬做。

### 7.2 开发中

每个开发任务按以下顺序执行：

1. 读产品规划和相关 PRD。
2. 查 `参考源码` 是否有可借鉴结构。
3. 读当前代码。
4. 写最小实现方案。
5. 修改代码。
6. 补测试。
7. 跑自动化测试。
8. 做手工验收。
9. 更新文档和发布说明。

### 7.3 迭代验收

每轮验收回答：

- 本轮目标是否达成？
- 用户能不能感知到价值？
- 自动化测试是否通过？
- 是否有未关闭风险？
- 是否需要发布？
- 是否影响下轮规划？

### 7.4 迭代复盘

每轮复盘只保留三类结论：

- 继续保持
- 立即修正
- 下轮验证

复盘不写空话，必须落到具体动作。

## 8. 版本发布流程

### 8.1 发布前检查

发布前必须完成：

- `npm test` 全部通过。
- 关键用户路径手工验收。
- 包内品牌词和测试数据扫描。
- OpenClaw 等高权限能力保持符合当前策略。
- README、操作说明书、发布说明更新。
- 发布产物 SHA256 记录。

### 8.2 发布目录

每个正式版本建立独立目录：

```text
产品发布\v1.0.1
├─ desktop-release
├─ source
├─ release-notes
└─ verification
```

### 8.3 发布记录

每个版本至少记录：

- 版本目标
- 新增能力
- 修复问题
- 已知边界
- 测试结果
- 包哈希
- 回退方案

## 9. 质量保障

### 9.1 自动化测试

最低要求：

- 后端核心逻辑必须有测试。
- 数据迁移、备份恢复、权限、Agent 派发必须有测试。
- 修复 bug 时优先补回归测试。

### 9.2 手工验收

每个版本至少覆盖：

- 首次启动
- 创建项目
- Agent 检测
- 本地任务派发
- 阶段回执
- 备份恢复
- 发布包启动

### 9.3 风险门禁

以下功能必须有二次确认或明确风险提示：

- 本地文件写入
- 命令执行
- 目录授权
- OpenClaw 初始化
- 备份恢复
- 删除项目
- 发布上线

## 10. 指标体系

指标只用于观察系统，不用于评价个人。

### 10.1 产品指标

- 从创建项目到首次完成任务的时间
- Agent 派发成功率
- 阶段回执完成率
- 人工验收通过率
- 备份恢复成功率
- 用户手动补救次数

### 10.2 工程指标

参考 DORA：

- 变更前置时间：从提交到可发布所需时间。
- 部署频率：正式版本或预览版本发布频率。
- 变更失败率：发布后需要修复或回退的比例。
- 失败恢复时间：从发现故障到恢复可用的时间。

### 10.3 流程指标

- 需求从提出到进入开发的周期
- 被砍掉或延期的需求比例
- 每轮迭代未完成任务数量
- 重复返工次数
- 参考源码复用次数

## 11. 角色分工

### 产品负责人

- 维护产品方向和版本规划。
- 决定做什么、不做什么。
- 保证需求有业务价值。

### 技术负责人

- 维护架构边界和技术方案。
- 决定关键技术取舍。
- 审核高风险改动。

### 开发执行者

- 实现功能。
- 补充测试。
- 更新开发记录。
- 主动报告风险。

### 测试 / 验收负责人

- 维护测试用例。
- 执行版本验收。
- 记录缺陷和回归结果。

### Agent / 自动化执行器

- 执行受控任务。
- 生成报告。
- 协助回归测试。
- 不替代最终人工确认。

## 13. 开发任务清单

每个开发任务必须按以下清单关闭：

```text
[ ] 已阅读相关产品规划/PRD
[ ] 已检查参考源码
[ ] 已明确本轮范围和不做范围
[ ] 已完成实现
[ ] 已补充或更新测试
[ ] 已通过自动化测试
[ ] 已完成关键路径手工验收
[ ] 已更新文档/说明书/发布说明
[ ] 已归档产物或中间数据
```

## 14. 目录落地规则

```text
产品规划
  00-产品理念       产品愿景、设计理念、命名含义
  01-调研资料       调研、竞品、流程分析、需求映射
  02-PRD            PRD、Pitch、需求说明
  03-版本规划       Roadmap、版本计划、范围冻结

产品开发
  nomos-desktop     当前桌面客户端源码
  测试用例          手工/验收测试用例
  测试报告          每轮迭代和每个版本的测试报告
  中间数据          实验数据、临时分析、过程文件

产品发布
  vX.Y.Z            正式版本产物
  GitHub源码        上传 GitHub 的源码归档或镜像
  发布说明          对内/对外版本说明

参考源码
  外部项目源码和分析笔记
```

## 15. 第一个执行版本建议

下一轮建议先建立以下文件：

```text
产品规划\03-版本规划\ROADMAP_V1.md
产品规划\02-PRD\PRD_V1_WORKFLOW_ENGINE.md
产品开发\测试用例\V1核心路径测试用例.md
产品开发\测试报告\v1.0.1-目录整理验收.md
产品发布\v1.0.1\release-notes\RELEASE-NOTES.md
```

这样 Nomos 后续开发就能从“能跑”进入“能管理、能复盘、能持续演进”的状态。
