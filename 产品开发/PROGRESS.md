| macOS 本机工具发现 | 已完成 | 本地命令探测从 `where.exe` 扩展为 Windows/macOS 通用逻辑，`git` 状态读取改为跨平台命令 |
| Kimi 本机适配器 | 已完成 | 新增 Kimi 技术适配器与硅基员工模板，支持命令检测、配置覆盖和本地执行派发 |

| CLI 工作项执行 | 已完成 | Codex CLI、Claude Code、Kimi 复用本地执行预览/确认/取消/重试链路，执行开始和结束会回写工作项负责人、状态和进度 |
| Alice 工作项协作 | 已完成 | Alice 支持工作项协作消息预览和显式确认，确认后写入工作项事件与项目消息 |

### 关键决策

1. **保留旧 bridge API，内部先接口化**：对外继续兼容 `/api/bridge`、`/api/executions` 和 Alice 派发接口；对内先把本机 Agent 细节收敛到 Adapter 注册表，避免前端和测试大面积震动。
2. **工作项派发不复用阶段任务信封**：从工作项发起的 CLI 执行不会自动绑定当前项目阶段，避免在代码开发阶段误污染阶段级 `workflowTasks`。
3. **Kimi 作为本机长上下文分析员接入**：默认命令为 `kimi`，可在桥接设置中覆盖命令入口；具体 CLI 参数后续可继续通过 Adapter 实现细化。
4. **Alice 工作项派发先走协作消息**：本轮不强行把工作项转换为阶段任务，只记录协作派发事实、工作项状态和项目消息，为后续工作项级回执同步预留空间。

### 下一步

- 将工作项派发记录沉淀为独立 `agentDispatches[]`，补充幂等、重试和回执聚合视图。
- 为 Kimi 增加可配置 invocation 模板，以适配不同本机 Kimi CLI 形态。
- 在工作项详情中展示派发历史、执行记录和 Alice 会话同步入口。

### 关键决策

1. **不重写 v1.2 流程实例结构**：当前代码以 `project.flowTemplateId + project.flowStages` 承载项目级流程实例。v1.3 对外保留 `flowInstanceId` 字段，但在当前版本中将其映射为 `project.id`，为 v2.0 独立运行时迁移预留接口。
2. **失败更新先校验后提交**：工作项更新先在副本上完成依赖、状态和父级校验，通过后再写回真实对象，确保 409/400 不会污染内存状态。
3. **旧任务按需镜像**：迁移只补空数组，不强制一次性生成所有镜像；工作项列表、看板和显式同步接口会按需生成，避免打开旧数据时产生不可控写入。
4. **V1.3 不做 Agent 自动派发**：本版只沉淀工作项事实、事件和看板，Agent 工作项级派发留到 v1.4。

### 下一步（v1.4 规划）

- 任务信封 v2、结构化回执 v2、派发幂等与重试。

## v1.2.0 — 流程管理版

### 开发周期

- 起止：2026-06-05 至 2026-06-07
- 对应 PRD：`产品规划/02-PRD/PRD_V1_FLOW_MANAGEMENT.md`

### 各模块完成状态

| 模块 | 状态 | 说明 |
|------|------|------|
| 流程模板库 CRUD | 已完成 | 创建、编辑、删除、复制、按分类浏览、搜索筛选 |
| 流程模板编辑器 | 已完成 | 阶段序列拖拽排序、关口配置、角色绑定、输入输出定义 |
| 预设模板 | 已完成 | "LTC 轻量版" 和 "项目交付" 两个默认模板 |
| 项目绑定流程 | 已完成 | 创建项目时可选模板，自动实例化阶段序列 |
| 流程实例运行 | 已完成 | 阶段推进、关口评审触发、退回返工逻辑 |
| 流程实例追踪 | 已完成 | 独立面板、阶段时间线可视化、状态筛选 |
| 关口评审 | 已完成 | 碳/硅/碳硅三种评审方式，通过/不通过/返工三种结果 |
| 数据迁移 v7→v8 | 已完成 | 自动补全 `flowTemplates: []`，向后兼容 |
| 集成测试 | 已完成 | 覆盖模板 CRUD、绑定/更换、评审流转、删除关联检查 |
| 回归测试 | 已完成 | 项目、工作流、Agent 路由、Alice 派发、本地执行、备份恢复、组织管理 |

### 关键决策

1. **流程数据存储方式**：沿用单一 `nomos-data.json` 文件持久化，不新增独立 JSON 文件。在 `data` 对象中新增 `flowTemplates` 数组，现有 `projects[]` 扩展 `flowTemplateId` 和 `flowStages` 字段。这样保持了与 v1.1 一致的存储架构，降低了迁移复杂度。

2. **新旧流程隔离策略**：绑定流程模板的项目走新流程引擎，不绑定的项目继续沿用现有五阶段交付链路，完全隔离。这一决策确保了 v1.2 的发布不会影响任何现有项目的数据和行为。

3. **关口评审不替换状态机**：关口作为现有工作流状态机的扩展层存在，不替换底层状态机。评审结果通过更新 `gateStatus` 和触发阶段推进来实现，保持了与工作流系统的兼容性。

4. **准入准出条件采用文本描述**：v1.2 不做规则引擎，准入条件和准出标准以文本描述存储。评审时由人工或 Agent 基于文本判断，而非自动规则校验。这降低了 v1.2 的实现复杂度，同时为 v2.0 的规则引擎预留了字段结构。

### 遇到的问题与解决方案

| 问题 | 解决方案 |
|------|---------|
| 流程模板编辑器需要支持阶段拖拽排序，但现有前端没有拖拽组件 | 使用原生 HTML5 Drag and Drop API 实现阶段列表拖拽排序，未引入外部依赖，减少包体积。 |
| 项目更换流程模板时，已有阶段数据可能与新模板不匹配 | 更换模板时弹出确认提示，说明阶段数据将重置；用户确认后重新实例化阶段序列，旧阶段数据保留在项目历史中但不再参与流程运行。 |
| 删除被引用的流程模板会导致关联项目数据不一致 | 删除前检查 `flowTemplateId` 引用计数，如有项目正在使用则拒绝删除并提示先解绑。 |
| 关口评审状态需要与工作流阶段状态同步 | 将 `gateStatus` 作为阶段对象的子字段，评审通过后再触发阶段推进，保持两个状态机的层级关系。 |
| v7→v8 数据迁移需要兼容无流程数据的旧版本 | `migrateData()` 中增加 `if (!data.flowTemplates) data.flowTemplates = [];`，确保旧数据打开时自动补全新字段。 |
