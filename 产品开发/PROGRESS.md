### 关键决策

1. **流程数据存储方式**：沿用单一 `nomos-data.json` 文件持久化，不新增独立 JSON 文件。在 `data` 对象中新增 `flowTemplates` 数组，现有 `projects[]` 扩展 `flowTemplateId` 和 `flowStages` 字段。这样保持了与 v1.1 一致的存储架构，降低了迁移复杂度。

2. **新旧流程隔离策略**：绑定流程模板的项目走新流程引擎，不绑定的项目继续沿用现有五阶段交付链路，完全隔离。这一决策确保了 v1.2 的发布不会影响任何现有项目的数据和行为。

3. **关口评审不替换状态机**：关口作为现有工作流状态机的扩展层存在，不替换底层状态机。评审结果通过更新 `gateStatus` 和触发阶段推进来实现，保持了与工作流系统的兼容性。

4. **准入准出条件采用文本描述**：v1.2 不做规则引擎，准入条件和准出标准以文本描述存储。评审时由人工或 Agent 基于文本判断，而非自动规则校验。这降低了 v1.2 的实现复杂度，同时为 v2.0 的规则引擎预留了字段结构。

### 遇到的问题与解决方案

| 问题 | 解决方案 |
|------|---------|
| 流程模板编辑器需要支持阶段拖拽排序，但现有前端没有拖拽组件 | 使用原生 HTML5 Drag and Drop API 实现阶段列表拖拽排序，未引入外部依赖，减少包体积。 |
| 项目更换流程模板时，已有阶段数据可能与新模板不匹配 | 更换模板时弹出确认提示，说明阶段数据将重置；用户确认后重新实例化阶段序列，旧阶段数据保留在项目历史中但不再参与流程运行。 |
| 删除被引用的流程模板会导致关联项目数据不一致 | 删除前检查 `flowTemplateId` 引用计数，如有项目正在使用则拒绝删除并提示先解绑。 |
| 关口评审状态需要与工作流阶段状态同步 | 将 `gateStatus` 作为阶段对象的子字段，评审通过后再触发阶段推进，保持两个状态机的层级关系。 |
| v7→v8 数据迁移需要兼容无流程数据的旧版本 | `migrateData()` 中增加 `if (!data.flowTemplates) data.flowTemplates = [];`，确保旧数据打开时自动补全新字段。 |
