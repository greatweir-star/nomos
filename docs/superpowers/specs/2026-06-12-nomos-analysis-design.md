## 二、三个方案

### 方案A：前端工程化重构（推荐）

**目标**：拆分 app.js 和 index.html，引入模块化或轻量框架。

**范围**：
- 将 app.js 按页面/功能拆分为独立模块
- 将 index.html 的样式提取为独立 CSS 文件
- 引入 ES Module 或轻量前端框架（如 petite-vue / Alpine.js）
- 保持 local-first 原则，不引入构建复杂度

**优势**：
- 降低单文件维护成本
- 提高代码可读性和可测试性
- 为后续功能扩展打基础

**劣势**：
- 需要改动前端架构，有一定风险
- 可能需要引入构建步骤（与当前"无构建"理念冲突）

**预计周期**：2 周

---

### 方案B：后端模块化拆分

**目标**：拆分 server.js，按业务模块组织路由。

**范围**：
- 将 server.js 按 API 模块拆分为独立文件
- 引入简单的路由分发器（无需 Express，保持原生 http）
- 将测试按模块拆分

**优势**：
- 降低单文件复杂度
- 模块间边界清晰
- 测试更容易定位问题

**劣势**：
- 需要改动后端入口，风险较高
- 47 项测试需要同步调整

**预计周期**：1-2 周

---

### 方案C：并行推进（A + B + v2.0 准备）

**目标**：工程化重构 + 为 v2.0 Workflow 引擎做准备。

**范围**：
- **主线（前端）**：拆分 app.js，引入 ES Module
- **主线（后端）**：拆分 server.js，模块化路由
- **并行（v2.0 准备）**：设计 Workflow 引擎 L2-L5 分层架构
- **并行（测试）**：补充单元测试，降低对端到端测试的依赖

**优势**：
- 一次性解决工程债务
- 为 v2.0 大版本升级做准备
- 测试覆盖更全面

**劣势**：
- 改动面广，需要更长的验证周期
- 可能影响当前 v1.3.0 的稳定性

**预计周期**：3-4 周

## 三、推荐方案

**推荐方案C（并行推进）**，理由：

1. app.js 181KB 和 server.js 83KB 是客观的技术债务，不处理后续越来越难改
2. v2.0 Workflow 引擎是产品下一步的核心，现在做准备可以避免重构两次
3. 47 项测试全部通过是重构的底气，可以边拆边验证

## 六、风险评估

| 风险 | 影响 | 缓解 |
|------|------|------|
| 拆分引入回归 | 高 | 47 项测试打底，逐模块迁移，每步验证 |
